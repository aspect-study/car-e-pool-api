00

Why events at all

The problem this pattern solves, in two sentences.

A user registers. You want to send them a welcome message. The obvious move is to call the messaging code directly inside register(). That breaks in two ways:

  • The message goes out, then the transaction rolls back. You just welcomed a user that doesn't exist in the database.
  • A slow network call holds your transaction open. The DB connection sits idle in the pool while you wait on someone else's API.

Events fix both. The service says "a user registered" and moves on. Separate code listens, and only runs after the commit succeeds, on its own thread.

What you'll build

A tiny Spring Boot app where POST /users saves a row, and two unrelated listeners react after the commit — one prints a welcome, one writes an audit line. Neither knows the other exists.

01

Create the project

One command, no IDE required.

terminal
curl https://start.spring.io/starter.zip \
  -d dependencies=web,data-jpa,h2 \
  -d javaVersion=21 \
  -d type=maven-project \
  -d name=events-demo \
  -d packageName=com.example.eventsdemo \
  -o events-demo.zip

Unzip it. Prefer clicking? Go to start.spring.io and pick Spring Web, Spring Data JPA, and H2 Database.

You get this:

events-demo/ ├── pom.xml └── src/main/ ├── java/com/example/eventsdemo/ │ └── EventsDemoApplication.java └── resources/ └── application.properties
Three dependencies, three jobs

Web gives you REST controllers. Data JPA gives you repositories and transactions. H2 is a throwaway database that lives in memory — nothing to install, nothing to clean up.

02

Configure the database

Three lines. Then forget about it.

src/main/resources/application.properties
spring.datasource.url=jdbc:h2:mem:demo
spring.jpa.hibernate.ddl-auto=update
spring.h2.console.enabled=true

ddl-auto=update tells Hibernate to create your tables from your entity classes at startup. Fine for a demo — real projects use Flyway migrations instead.

03

The entity

One table, two columns.

com/example/eventsdemo/User.java
package com.example.eventsdemo;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    protected User() {}   // JPA requires a no-arg constructor

    public User(String name) {
        this.name = name;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }
}
Watch out

The protected User() {} is not optional. JPA constructs entities reflectively and needs a no-arg constructor. Leave it out and you get a startup failure that reads nothing like the actual cause.

04

The repository

An empty interface that does a surprising amount.

com/example/eventsdemo/UserRepository.java
package com.example.eventsdemo;

import org.springframework.data.jpa.repository.JpaRepository;

public interface UserRepository extends JpaRepository<User, Long> {}

You write zero methods. Spring generates the implementation at startup and hands you save(), findById(), findAll(), delete() and friends.

05

The event

The whole thing is one line.

com/example/eventsdemo/UserRegisteredEvent.java
package com.example.eventsdemo;

public record UserRegisteredEvent(User user) {}

No annotation. No interface to implement. No base class to extend. A record is a small immutable carrier — perfect, because an event describes something that already happened and must never be edited afterward.

Naming

Past tense, always: UserRegisteredEvent, not RegisterUserEvent. An event is a fact, not a command. Nobody can veto it.

06

Publish it

Inject the publisher, fire after the save.

com/example/eventsdemo/UserService.java
package com.example.eventsdemo;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class UserService {

    private final UserRepository userRepository;
    private final ApplicationEventPublisher eventPublisher;

    public UserService(UserRepository userRepository,
                       ApplicationEventPublisher eventPublisher) {
        this.userRepository = userRepository;
        this.eventPublisher = eventPublisher;
    }

    @Transactional
    public User register(String name) {
        User saved = userRepository.save(new User(name));

        eventPublisher.publishEvent(new UserRegisteredEvent(saved));

        return saved;
    }
}
1Add ApplicationEventPublisher as a constructor parameter — Spring injects it, you never create it.
2Save first, publish second. The event should carry the saved entity, so it has a real database ID.
3Keep @Transactional on the method. It's what makes "after commit" mean anything in step 07.
Key insight

publishEvent(...) does not run anything yet. It registers the event with the current transaction. Nothing happens until the method returns and the commit lands.

07

The listener

Two annotations do all the work.

com/example/eventsdemo/WelcomeListener.java
package com.example.eventsdemo;

import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Component;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;

@Component
public class WelcomeListener {

    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onUserRegistered(UserRegisteredEvent event) {
        System.out.println("Welcome, " + event.user().getName() + "!");
    }
}

Spring wires this up by the method's parameter type. No registration list, no config file. Publish a UserRegisteredEvent anywhere in the app and this method receives it.

AnnotationWhat it buys you
@ComponentMakes the class a Spring bean so it gets scanned. Without it, nothing is wired.
@AsyncRuns on a separate thread. Your HTTP response returns immediately; slow work doesn't block the caller.
@TransactionalEventListener(AFTER_COMMIT)Runs only after the publisher's transaction commits successfully. On rollback, it never runs at all.
The classic mistake

Using plain @EventListener instead. That fires immediately, inside the transaction — so it also fires on transactions that later roll back. That's exactly the "welcomed a user who doesn't exist" bug. Reach for @TransactionalEventListener(AFTER_COMMIT) by default.

08

Turn on async

One annotation, once, or @Async silently does nothing.

com/example/eventsdemo/EventsDemoApplication.java
package com.example.eventsdemo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.scheduling.annotation.EnableAsync;

@SpringBootApplication
@EnableAsync
public class EventsDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(EventsDemoApplication.class, args);
    }
}
Silent failure

Forget @EnableAsync and there's no error, no warning — your listener just runs on the caller's thread. Everything still works, so this can hide for months until something slow blocks a request.

09

Something to trigger it

A two-method REST controller.

com/example/eventsdemo/UserController.java
package com.example.eventsdemo;

import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping
    public User register(@RequestParam String name) {
        return userService.register(name);
    }
}
10

Run it

First proof that the wiring works.

terminal 1
./mvnw spring-boot:run
terminal 2
curl -X POST "http://localhost:8080/users?name=Alice"
Application console Welcome, Alice!

The HTTP response returns straight away with the saved JSON. The welcome line prints from a different thread, after the commit.

Prove it to yourself

Throw an exception at the end of register(), after the publishEvent line. The transaction rolls back and nothing prints — the listener never fires. Now swap @TransactionalEventListener(AFTER_COMMIT) for a plain @EventListener and try again: it prints, for a user that was never saved. That contrast is the entire lesson.

11

Hero move — two listeners, one event

Add a second reaction without touching the service.

com/example/eventsdemo/AuditListener.java
package com.example.eventsdemo;

import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Component;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;

@Component
public class AuditListener {

    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onUserRegistered(UserRegisteredEvent event) {
        System.out.println("Audit: user #" + event.user().getId() + " created");
    }
}

New file. Nothing else changed — UserService is untouched. Run the same curl:

Application console Welcome, Alice!
Audit: user #1 created
This is the payoff

One publish, N reactions. The service never learns who is listening. Adding a third behaviour — analytics, a Slack ping, a welcome email — is a new file and zero edits to existing code.

12

The gotcha: listeners that write to the DB

The one thing that will bite you in production.

The moment a listener saves something, you need a third annotation. After the commit there is no active transaction anymore — the old one is finished:

a listener that persists
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)   // starts a fresh transaction
public void onUserRegistered(UserRegisteredEvent event) {
    notificationRepository.save(
            new Notification(event.user().getId(), "WELCOME"));
}
Forget REQUIRES_NEW and…

You get an IllegalTransactionStateException at runtime — or worse, a silent no-op where the write is never flushed. This is the single most common bug in this pattern.

So the full stack, for a listener that both notifies and records:

the canonical three-annotation stack
@Async                                                   // own thread
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)  // only after commit
@Transactional(propagation = Propagation.REQUIRES_NEW)   // fresh transaction to write in
Order matters

Spring applies @Async first (new thread), then @Transactional opens the new transaction inside that thread. Keep them in this order and it reads the way it executes.

13

The same pattern, in the real project

Everything above, scaled up — nothing new to learn.

In the carpool codebase, a driver changing a ride's route follows exactly these steps. Only the field count changes:

TutorialCarpool project
UserRegisteredEventRideEvents.RideRouteChangedEvent — a record nested in one RideEvents holder class
UserService.register()RideService.updateRoute() — validates, locks the row, saves, then publishes
WelcomeListenerNotificationService.onRideRouteChanged — DMs each confirmed passenger
AuditListenerGroupNotificationService.onRideRouteChanged — refreshes the group announcement
the real event — three fields instead of one
public record RideRouteChangedEvent(Ride ride,
                                    String oldOriginName,
                                    String oldDestinationName) {}

Why three? The service captures the old hub names before overwriting them, and ships them inside the event. By the time the listener runs, the entity has already changed — the event is the only surviving memory of the old route, which is what lets the passenger DM read "Was: A → B, Now: C → D".

The rule that generalises

If a listener needs to know something that the save destroyed, put it in the event. Events carry facts, not just entity references.

14

Cheat sheet

Everything, on one screen.

1Define the event — public record SomethingHappenedEvent(Entity e) {}
2Inject ApplicationEventPublisher into the service
3Call publishEvent(...) after the save, inside @Transactional
4Write a @Component with the three-annotation stack
5Make sure @EnableAsync is on the application class
6Need another reaction? New listener file. Never touch the publisher.

Rules worth memorising

RuleBecause
Name events in the past tenseAn event is a fact that already happened, not a request
Use records, never mutable classesMultiple listeners share the same instance — a mutation in one corrupts the others
Prefer @TransactionalEventListener(AFTER_COMMIT) over @EventListenerPlain @EventListener also fires for transactions that roll back
Add REQUIRES_NEW whenever the listener writesThere is no active transaction after commit
Never let a listener throw into the callerIt runs on another thread after commit — the exception is invisible. Wrap the risky part in try/catch and log it.
Publish once, react many timesThe publisher must never grow a list of things to notify
You're done

You built the pattern from an empty folder: an event, a publisher, two listeners, after-commit safety, and the transaction gotcha. That's the same machinery behind every ride notification, group announcement refresh, and audit row in the carpool project.
