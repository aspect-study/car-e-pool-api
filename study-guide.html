🔄 1.1 The Agentic Loop Lifecycle

An agent is not a single API call — it is a loop that continues until the model signals completion. Understanding stop_reason is the most tested concept in this domain.

⏹️ stop_reason Values

  • tool_use — model wants to call a tool; loop MUST continue by appending results
  • end_turn — model finished; loop should terminate
  • max_tokens — context limit hit; handle gracefully
  • stop_sequence — custom stop token matched; usually terminal

📜 Conversation History Rules

  • Tool results MUST be appended before the next API call
  • Role alternation: user → assistant → user → assistant
  • Tool result role = user, not tool
  • Never skip a tool result — the model loses context
  • Each tool result maps to its tool_use_id
🗺️ Canonical Loop Pattern
PYTHON — Canonical Agentic Loop (CCA-F Reference Pattern)
messages = [{"role": "user", "content": user_input}]

while True:
    response = client.messages.create(
        model="claude-opus-4-7",
        max_tokens=4096,
        tools=tools,
        messages=messages
    )

    # Always append the assistant's full response
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        # Model is done — extract final text and exit
        final = next(b.text for b in response.content if b.type == "text")
        break

    if response.stop_reason == "tool_use":
        # Execute every tool call the model requested
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,      # ← must match the request id
                    "content": result
                })

        # Append results as a USER message before the next call
        messages.append({"role": "user", "content": tool_results})
        # Loop continues — model now sees the results
    else:
        break  # max_tokens / stop_sequence — handle accordingly
[DANGER]

Anti-Pattern #1 — Skipping Tool Results

Calling the API again without appending the tool result is the most common agentic bug. The model re-enters without knowing what the tool returned, leading to hallucinated results or infinite loops. The exam will test this — always append results before the next call.

🔄 Loop Continue — tool_use analogue

In the bot, a "tool call" is any handler that mutates UserState and expects another user interaction to continue the flow:

  • handleDateSelected() → sets flow=DEPARTURE_TIME, sends time picker
  • handleRideTimeSelected() → sets flow=ORIGIN, sends hub list
  • Each step waits for the next update (next "tool result")

🛑 Loop Terminate — end_turn analogue

  • handleConfirmPostRide() → publishes ride, calls stateManager.reset()
  • handleCancelPostRide() → discards draft, calls stateManager.reset()

Architect Wisdom — Tool Choice Eliminates Ambiguity

When you need structured output, use tool_choice: {type: "tool", name: "..."} to force the model into a specific tool call. This is more reliable than asking the model to "respond in JSON" in a system prompt. The model cannot call a different tool, cannot return plain text — the structure is enforced at the protocol level, not via prompt persuasion.

🪝 1.3 PreToolUse / PostToolUse Lifecycle Hooks

Hooks fire before or after tool execution and can block, modify, or log. They enforce policies programmatically — stronger than system-prompt instructions because they execute outside model context.

🔒 Our settings.json Hook Config

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command",
                    "command": "bash .claude/hooks/guard-bash.sh" }]
      },
      {
        "matcher": "Write",
        "hooks": [
          { "type":"command","command":"bash .claude/hooks/flyway-gate.sh" },
          { "type":"command","command":"bash .claude/hooks/module-boundary-check.sh" }
        ]
      },
      {
        "matcher": "Edit",
        "hooks": [
          { "type":"command","command":"bash .claude/hooks/flyway-gate.sh" },
          { "type":"command","command":"bash .claude/hooks/module-boundary-check.sh" }
        ]
      }
    ],
    "Stop": [
      { "hooks": [{ "type":"command",
                    "command": "bash .claude/hooks/vault-writeback.sh" }] }
    ]
  }
}

🛡️ What Each Hook Enforces

  • guard-bash.sh — blocks rm -rf, DROP TABLE, --force-push
  • flyway-gate.sh — enforces V#__description.sql naming; blocks editing any existing migration file
  • module-boundary-check.sh — blocks illegal cross-module Java imports (e.g., carpool-bot importing carpool-web)
  • vault-writeback.sh — on session stop: auto-creates dispatch log in memory/dispatch-logs/
[TIP]

Exam Key

Hooks exit non-zero to block the tool call. Exit zero to allow. The model cannot override a blocking hook via prompting — this is the core advantage over system-prompt policies.

❌ Weak — Prompt-Only Policy

"IMPORTANT: Never edit existing Flyway
migration files. Always create new ones
with the next version number."

// Problem: Model can "forget", be confused
// by context, or be talked out of it.
// Zero enforcement at execution time.
✅ Strong — Hook-Enforced Policy

# flyway-gate.sh checks the target file path:

    exit 1
  fi
fi
# New file or non-migration → allow with exit 0

The Principle

A coordinator agent should pass only the minimum necessary context to each subagent. The coordinator synthesizes results itself — it does not dump its full conversation history into every subagent call. This keeps subagent prompts focused, reduces token cost, and prevents context poisoning.

✅ Correct — Targeted Handoff

"Add a NOT NULL column `group_message_posted_at

# - the relevant constraint
# No conversation history, no other modules' code.

[All 6 module CLAUDE.md files]

Architect Wisdom — Prompt vs Hook for Safety Policies

For any policy that protects data integrity (never drop a table, never edit a migration, never cross module boundaries), use a hook, not a prompt instruction. Prompts are advisory. Hooks are enforced. The exam distinguishes between "programmatic enforcement" (hooks, tool schema constraints, tool_choice) and "weak prompt guidance" (system prompt instructions asking the model to behave a certain way).

⚙️ 1.3 Task Tool & Subagent SpawningSD 1.3

The Task tool is the mechanism for spawning subagents from a coordinator. The coordinator must list "Task" in its allowedTools. Subagents do not automatically inherit parent context — every piece of information they need must be explicitly included in the prompt.

🔑 Task Tool Requirements

  • Coordinator's allowedTools must include "Task"
  • Subagent prompt must contain ALL needed context (no auto-inheritance)
  • Spawn parallel subagents by emitting multiple Task calls in ONE coordinator response
  • AgentDefinition: set description, system prompt, and tool restrictions per subagent role
  • Pass structured data (source URLs, document names, page numbers) — not raw conversation

🏗️ car-e-pool-api Parallel Agent Pattern

  • Claude Code as coordinator emitting TWO Agent calls in one message = parallel
  • Agent 1: db-engineer — reads V44 migration + Ride entity (isolated context)
  • Agent 2: qa — reads existing test files + patterns (different isolated context)
  • Both run concurrently — coordinator synthesizes both results
  • Coordinator's prompt specifies research goals and quality criteria — not step-by-step instructions

🔐 1.4 Programmatic Prerequisites & Handoff PatternsSD 1.4

For workflows where step ordering is safety-critical (identity verification before financial operations), prompt instructions have a non-zero failure rate. Programmatic prerequisites block downstream tool calls at the execution layer — not via persuasion.

❌ Prompt-Only Ordering (Probabilistic Failure)
# System prompt says:
"IMPORTANT: Always call get_customer first
before calling process_refund. Never skip
identity verification."

# Problem: under sufficient prompt pressure
# or context confusion, the model may call
# process_refund directly.
# Prompt instructions = probabilistic compliance.
# Critical workflows cannot rely on them.
✅ Programmatic Gate (Deterministic)
def process_refund(customer_id: str, amount: float):
    # Gate: block if prerequisite not satisfied
    if not session.has_verified_customer():
        return {
            "isError": True,
            "errorCategory": "PREREQUISITE_NOT_MET",
            "isRetryable": False,
            "message": "Call get_customer first to "
                       "verify identity before refund.",
            "requiredTool": "get_customer"
        }
    # Only executes after get_customer ran
    return execute_refund(customer_id, amount)

📋 Structured Handoff Summary

When escalating to a human agent who lacks conversation access, compile a structured handoff — never vague summaries:

  • customer_id — verified identity reference (exact ID)
  • root_cause — what was investigated and found
  • attempted_actions — what was tried and the outcome
  • refund_amount — specific number, never "approximately"
  • recommended_action — clear next step for the human agent

🔵 Project Parallel: BookingService Prerequisite Gate

  • createBooking() calls findByIdWithLock() before seat decrement
  • Pessimistic lock = the programmatic prerequisite gate
  • Without the lock, two concurrent requests pass the seat-check simultaneously → oversell
  • The lock is mandatory — seat decrement cannot safely proceed without it
  • H2 ignores SELECT FOR UPDATE → test the gate on real MySQL at port 3308
🔄 1.5 PostToolUse Hooks — Normalization & ComplianceSD 1.5

PostToolUse hooks intercept tool results after execution and before the model processes them. Use them to normalize heterogeneous formats from different MCP tools, or to intercept outgoing tool calls and enforce compliance rules.

📐 Normalization (PostToolUse)

  • MCP tools return different timestamp formats (Unix, ISO 8601, custom strings)
  • PostToolUse hook converts all to ISO 8601 before the model sees them
  • Status codes (0/1/2 vs "ACTIVE"/"FULL") normalized to human-readable values
  • Currency: 1000 vs PHP 1,000.00 → canonical form
  • Model reasons consistently because all inputs share one format

🚫 Compliance Interception (PreToolUse)

  • Hook intercepts a refund tool call before it executes
  • Checks amount against policy threshold (e.g., $500 max auto-approval)
  • Blocks the call and returns a redirect to human escalation workflow
  • Model cannot bypass this — enforcement happens outside model context
  • Key distinction: PreToolUse blocks calls; PostToolUse transforms results
PostToolUse Hook — Timestamp & Status Normalization (car-e-pool-api pattern)
# PostToolUse hook: normalize ride data BEFORE model processes it
# Fired AFTER tool returns, BEFORE model sees the result

def post_tool_use_normalizer(tool_name: str, tool_result: dict) -> dict:
    if tool_name in ("get_ride", "search_rides_by_direction"):
        rides = tool_result.get("rides", [])
        for ride in rides:
            # Normalize Unix timestamp → ISO 8601
            if isinstance(ride.get("departureTime"), int):
                ride["departureTime"] = datetime.utcfromtimestamp(
                    ride["departureTime"]
                ).strftime("%Y-%m-%dT%H:%M:%S")

            # Normalize numeric status → readable string
            status_map = {0: "DRAFT", 1: "ACTIVE", 2: "FULL", 3: "CANCELLED"}
            if isinstance(ride.get("status"), int):
                ride["status"] = status_map.get(ride["status"], "UNKNOWN")

    return tool_result  # normalized result goes to model

# Register in settings.json:
# "PostToolUse": [{
#   "matcher": "get_ride",
#   "hooks": [{"type":"command","command":"python normalize_ride.py"}]
# }]

# Hooks = deterministic normalization.
# Asking the model to "handle Unix timestamps" in the system prompt = probabilistic.
🗂️ 1.6 Task Decomposition StrategiesSD 1.6

🔗 Prompt Chaining (Fixed Sequential)

  • Break work into fixed sequential steps with defined inputs/outputs per step
  • Pattern: analyze each file individually → cross-file integration pass
  • Use when: steps are predictable, each output is well-defined
  • Best for: code reviews, schema migrations, document processing
  • Project: architect → db-engineer → qa sequential chain for a new feature

🌳 Dynamic Decomposition (Adaptive)

  • Generate subtasks based on what is discovered at each step
  • Pattern: map structure → identify high-impact areas → adapt plan as dependencies found
  • Use when: scope is open-ended, dependencies are unknown upfront
  • Best for: "add comprehensive tests to legacy codebase", bug root cause investigations
  • Project: investigating why rides are not appearing for a specific user
[INFO]

Exam Decision Rule — Chaining vs. Decomposition

Prompt chaining: use when the task is predictable — code review (file-by-file analysis + integration pass), Flyway migration (read V-max, write V-max+1, update entity). Dynamic decomposition: use when the scope is unknown upfront — "investigate a performance regression", "add missing test coverage to carpool-bot". The exam will describe a task — ask yourself: "Do I know all the steps in advance?" If yes → chaining. If the steps depend on what you find → dynamic decomposition.

💾 1.7 Session Resumption & ForkingSD 1.7

🔄 --resume <session-name>

  • Continues a named prior session with full conversation history
  • Use when: prior context is still valid (files haven't changed significantly)
  • Before resuming: explicitly inform the agent about any file changes since last session
  • Stale tool results (file content read in a prior session that has since changed) = #1 hazard
  • If files changed substantially: start fresh with a structured summary injection instead

🍴 fork_session

  • Creates independent branches from a shared analysis baseline
  • Both branches share the initial analysis but diverge from the fork point
  • Use when: comparing two competing implementation approaches
  • Example: fork after codebase analysis → Branch A: optimistic locking, Branch B: pessimistic locking
  • Each branch operates independently — no shared state after fork
Session Management — Resume vs. Start Fresh Decision Guide
# ✅ Use --resume: prior context is VALID (same day, no file changes)
claude --resume "carpool-booking-investigation"
# Immediately tell the agent what changed since last session:
# "Since last session: BookingService.createBooking() was updated at line 87.
#  Re-analyze only that method — prior analysis of other methods is still valid."

# ✅ Start fresh: prior tool results are STALE (files changed, day-old session)
claude -p """
Summary from prior session (inject manually — don't resume stale session):
- BookingService uses findByIdWithLock() (SELECT FOR UPDATE) at line 87
- Ride entity has: seats INT, version INT (optimistic lock column)
- Confirmed problem: oversell race condition under concurrent load at > 50 rps

New task: implement the fix. Files to review: BookingService.java, RideRepository.java
"""
# Injecting summary = reliable. Resuming with stale tool outputs = confusing.

# ✅ fork_session: exploring competing approaches from shared baseline

# Branch B: pessimistic locking with SELECT FOR UPDATE (current approach)

The application that embeds Claude (Claude Code, your IDE, your app). Manages the MCP client lifecycle. In our project: Claude Code CLI is the host when you run it in car-e-pool-api/.

Exposes Tools, Resources, and Prompts to the model. Can be a local process (stdio) or remote HTTP server. Example: @modelcontextprotocol/server-github gives Claude GitHub API access.

🎯 2.3 Tool Distribution & tool_choice ConfigurationSD 2.3

Giving an agent too many tools degrades selection reliability by increasing decision complexity. An agent with 18 tools will misuse tools outside its specialization — a synthesis agent given web search tools will search instead of synthesizing. Target: 4–5 tools per agent role.

📊 Tool Count Limit — Why 4–5 Max

  • More tools = higher decision complexity = lower selection accuracy
  • Synthesis agents with fetch_url will use it instead of synthesizing
  • Scoped access: each agent gets only the tools relevant to its role
  • Cross-role tools only for specific high-frequency needs (e.g., verify_fact for synthesis agent)
  • Complex cross-role cases route through the coordinator — not via direct tool access

⚙️ tool_choice Options

  • "auto" — model may call a tool OR return text (default; flexible)
  • "any" — model MUST call a tool; chooses which one (guarantees tool use, not text)
  • {"type":"tool","name":"..."} — forced: model MUST call that specific named tool
  • Use "any" when: multiple schemas exist and document type is unknown upfront
  • Use forced when: a specific extraction must happen first (e.g., extract_metadata before enrichment)

🔁 3.11 Stop Hook Feedback Loop — Active vs Passive HooksSD 3.11

Not all Stop hooks are passive observers. A Stop hook that outputs {"systemMessage": "..."} to stdout feeds that text back to Claude as a system-level message on the next turn. This turns the hook into an active feedback loop — Claude sees the error and can self-correct without manual intervention.

🔍 Two Stop Hook Patterns

  • Passive / Observational: logs data, creates audit files, sends notifications — exit 0, no stdout output. Claude is unaware it ran.
  • Active / Feedback: runs a check after each turn, outputs {"systemMessage": "…"} if problems found — Claude reads this on its next prompt and can self-correct.
  • vault-writeback.sh = passive (creates dispatch log, no stdout to Claude)
  • compile-check.sh = active (outputs compile errors as systemMessage)

⚙️ compile-check.sh Pattern

  • Runs mvn test-compile -DskipTests -q after every Claude turn
  • Fires once per turn — all files are already written before the check runs
  • On success: exits 0, no output → Claude is not interrupted
  • On failure: outputs {"systemMessage": "COMPILATION ERRORS — …"} → Claude sees the errors at the top of the next prompt and self-corrects
  • Key: the hook always exits 0 — it never blocks the turn, only informs the next one
compile-check.sh — Stop Hook as Active Feedback Loop
#!/usr/bin/env bash
# Stop hook — runs mvn test-compile after Claude finishes a turn.
# Fires once per turn (all files written before this runs).
# Outputs systemMessage JSON so Claude sees errors on the next turn.

OUTPUT=$(mvn test-compile -DskipTests --no-transfer-progress -q 2>&1)
EXIT_CODE=$?

if [ $EXIT_CODE -ne 0 ]; then
  MSG="COMPILATION ERRORS — fix before running tests:
$OUTPUT"
  # systemMessage key = Claude reads this as a system-level prompt on next turn
  python3 -c "
import json, sys
msg = sys.stdin.read()
print(json.dumps({'systemMessage': msg}))

🧪 3.12 Hard-Won Integration Test GotchasSD 3.12

These patterns were learned from real failures in carpool-web integration tests. Each is a non-obvious trap that will likely appear in exam scenarios about agentic code generation quality and test infrastructure design.

🔒 @Transactional on BaseIntegrationTest

  • Problem: each test inserts rows; without cleanup, later tests see leftover data and produce false results
  • Fix: add @Transactional to BaseIntegrationTest — Spring rolls back each test's transaction automatically after the test method exits
  • Exam angle: agentic code generation that creates integration tests must inherit from a transactional base class; not doing so causes cross-test DB pollution
  • Anti-pattern: relying on @AfterEach deleteAll() calls — order-dependent, breaks on test failure before cleanup

⚡ NOT_SUPPORTED Propagation for Concurrency Tests

  • Problem: a pessimistic lock test wrapped in an outer @Transactional never actually contends — both threads share the same outer transaction and the lock is never released between calls
  • Fix: annotate the concurrency test method with @Transactional(propagation = Propagation.NOT_SUPPORTED) — suspends the outer transaction so each thread gets its own real transaction and lock
  • Exam angle: understanding transaction propagation is critical for validating concurrency guarantees at the integration test level

🗺️ MapStruct Silent Null Without @Mapping

  • Problem: MapStruct generates mapper code at compile time. If a target field has no matching source field name AND no explicit @Mapping annotation, MapStruct silently sets it to null — no warning, no error
  • Fix: always add explicit @Mapping(source = "...", target = "...") for every non-trivial field in the mapper interface
  • Project example: EntityMapper.toRatingResponse() and toUserSummaryResponse() produced all-null DTOs until explicit @Mapping annotations were added
  • Exam angle: compile-time code generation tools can introduce runtime null silently — a CI compile check alone won't catch this; only integration tests that assert field values will

🍴 forkCount=0 in Surefire — Java Version Fork Issue

  • Problem: Maven Surefire's default forked JVM uses the JVM it discovers on PATH, which may differ from the Java version used to build the project — causing cryptic UnsupportedClassVersionError or module-path failures in integration tests
  • Fix: add <forkCount>0</forkCount> to the Surefire plugin config — runs tests in the same JVM as Maven, guaranteeing version consistency
  • Trade-off: no process isolation between test runs; a JVM crash kills all tests. Acceptable for local dev and CI where version consistency matters more than isolation
[TRAP]

Typed Exceptions Over Raw IllegalArgumentException

When an agentic pipeline generates service code, it will often throw IllegalArgumentException or IllegalStateException as generic error signals. This is an anti-pattern — exception handlers in GlobalExceptionHandler cannot distinguish a booking conflict (409) from a bad request (400) if both throw IllegalStateException.

  • Correct pattern: typed exception per HTTP status: InvalidOperationException → 400, RatingConflictException → 409, ResourceNotFoundException → 404, NotRideOwnerException → 403
  • Exam angle: when reviewing AI-generated service code, the first thing to check is whether raw exceptions are being thrown where typed ones should be used — this is a predictable AI code generation flaw

Vague instructions like "be conservative" or "only report high-confidence findings" do NOT improve precision. They require the model to guess what "high confidence" means. The current AiService.parseRideRequest() in the project uses a Spring AI ChatClient with an inline system prompt. Here's how to structure it optimally:

JAVA — Optimized AiService System Prompt Structure
// carpool-service/ai/AiService.java
@Service
public class AiService {

    // System prompt components — ordered for cache efficiency:
    // 1. Static role + context (most cacheable)
    // 2. Semi-static rules (cacheable within session)
    // 3. Dynamic per-request data (never cached)

    private static final String SYSTEM_STATIC = """
        You are a ride-detail extractor for a Philippine carpooling app.
        The app serves commuters in Metro Manila.
        Users write in Filipino, Taglish, or English.

        Key domain facts:
        - "Home to work" direction = morning commute, before noon
        - "Work to home" direction = evening commute, after noon
        - Common locations: Sucat, Paranaque, BGC, Makati, Taguig, QC
        - Filipino time words: "bukas"=tomorrow, "ngayon"=today, "mamaya"=later today
        - "Magpost"/"mag post" indicates intent to post a ride (driver)
        """;

    private static final String EXTRACTION_RULES = """
        Extraction rules:
        1. If direction is ambiguous, infer from time (morning=HOME_TO_WORK, evening=WORK_TO_HOME)
        2. If a field cannot be determined, return null — do not guess
        3. Times are 24h format. "7am"=07:00, "6pm"=18:00
        4. Seats: look for numbers near "seat", "tao", "pasahero"
        5. Contribution: look for peso amounts near "each", "tig", "per person"
        """;

    public ParsedRideRequest parseRideRequest(String userMessage) {
        // System prompt = static + rules (both cache-eligible)
        // User message = dynamic (never cached, always appended)
        return chatClient
            .prompt()
            .system(SYSTEM_STATIC + "\n" + EXTRACTION_RULES)
            .user(userMessage)
            .call()
            .entity(ParsedRideRequest.class);
    }
}

💰 5.1 Strategic Prompt Caching

Prompt caching stores processed prompt segments on Anthropic's servers for 5 minutes (Haiku) or longer (Opus/Sonnet). Cached tokens cost ~10% of normal input token price. The key skill is knowing where to place cache breakpoints.

📍 Cache Breakpoint Rules

  • Breakpoints are placed at the end of a static section
  • Everything before a breakpoint is eligible for caching
  • Dynamic content (user input, timestamps) goes AFTER the last breakpoint
  • TTL: 5 minutes — re-use within 5 min = cache hit
  • Max 4 cache breakpoints per request

💸 Cost Model

  • Cache write: 1.25× normal input cost (paid once)
  • Cache hit: ~0.10× normal input cost (paid each reuse)
  • Break-even: ~2 requests to recoup write cost
  • Best for: system prompts, long code files, tool definitions that don't change per request

real MySQL at localhost:3308.

BookingService. If adding a new booking-like feature (e.g., waitlist),
use the same lock acquisition pattern. See [[adr-003-event-listeners]]

The mental model for prompt caching: anything that would be the same across 10 API calls should be cached. 📌 5.1 Long Conversation Context — Case Facts & Lost-in-MiddleSD 5.1

As conversations grow, two distinct problems emerge: progressive summarization loss (specific numbers and dates become vague) and the "lost in the middle" effect (models reliably process the beginning and end of long inputs, but miss content in the middle sections).

📋 Case Facts Block Pattern

  • Extract transactional facts (amounts, dates, order IDs, statuses) into a persistent block
  • Include this block in every prompt — outside the summarized conversation history
  • Prevents vague summaries like "a large refund" when the actual value was "₱2,450"
  • For multi-issue sessions: persist structured issue data in a separate context layer
  • Project parallel: persist ride IDs, booking IDs, and seat counts as explicit facts — never summarize them away

📍 Mitigating Lost-in-Middle

  • Place key findings summaries at the beginning of aggregated inputs
  • Organize detailed results with explicit section headers so middle content is locatable
  • Trim verbose tool outputs: keep only relevant fields before they accumulate in context
  • Example: order lookup returns 40+ fields — keep only the 5 return-relevant fields
  • Require subagents to include metadata (dates, source locations) in structured outputs
Persistent Case Facts Block Pattern (carpool support context)
# ✅ Case facts block — included in every prompt, never summarized away
CASE_FACTS_BLOCK = """
=== ACTIVE CASE FACTS ===
User: Oliver Lapapa (telegram_id: 88123456)
Ride ID: 4421 | Direction: HOME_TO_WORK | Date: 2026-05-26 07:00
Booking ID: 1183 | Seats booked: 2 | Status: CONFIRMED
Issue reported: Seat count shows 0 in user's view after booking
Investigated at: 2026-05-25T14:32:00
Findings so far: findByIdWithLock() returned ride.seats=2, booking.seats=2
  but RideResponse.availableSeats=0 (possible mapper bug in EntityMapper)
"""

# System prompt structure:
messages = [{
    "role": "user",
    "content": f"""{CASE_FACTS_BLOCK}

Conversation history (summarized):
{summarized_history}

Current user message: {current_message}
"""
}]
# Case facts are ALWAYS present — even when history is compressed.
# Numbers never become "some seats" — they stay "2 seats" and "0 available".

# Trim verbose tool output BEFORE it enters context:
raw_ride_response = get_ride(4421)  # returns 40+ fields
# ✅ Keep only what matters for THIS task:
trimmed = {k: raw_ride_response[k]

⚠️ 5.3 Error Propagation Across Multi-Agent SystemsSD 5.3

When a subagent fails, the coordinator needs structured error context — not just a status string — to make intelligent recovery decisions. Two distinct failure types must be reported differently: access failures (retry decisions) vs. valid empty results (successful queries with no matches).

❌ Generic Error (Coordinator Cannot Recover)
# Subagent returns to coordinator:
{
  "status": "error",
  "message": "search unavailable"
}
# Coordinator doesn't know:
# - Was it a timeout? Rate limit? Permissions error?
# - Should it retry immediately? After delay? Never?
# - Was there partial data before the failure?
# - What alternative approaches exist?
✅ Structured Error Context (Coordinator Can Recover)
{
  "status": "error",
  "failure_type": "TIMEOUT",
  "attempted_query": "rides WHERE date='2026-05-26'",
  "partial_results": [{"id": 4418}, {"id": 4419}],
  # partial results up to the timeout
  "retry_recommendation": "retry_after_30s",
  "alternative_approach": "query_by_driver_id_instead",
  "what_was_attempted": "full table scan — consider indexed query"
}
# Coordinator now knows: retry in 30s, use partial results meanwhile,
# or fall back to indexed query. Intelligent recovery is possible.

🔄 Local Recovery First

  • Subagents should implement local recovery for transient failures (retry ×3 with backoff)
  • Only propagate errors that cannot be resolved locally
  • Include what was attempted and partial results when propagating
  • Structure synthesis output with coverage annotations: which findings are well-supported vs. which areas have gaps due to unavailable sources

⚖️ Access Failure vs. Valid Empty Result

  • Access failure: timeout, permission denied → coordinator needs retry decision
  • Valid empty result: query succeeded, zero matches → coordinator knows the data doesn't exist
  • Silently returning empty results for an access failure = coordinator thinks no data exists = wrong recovery
  • Always distinguish these two cases explicitly in the return value

D1Agentic Loop Controlstop_reason drives loop continuation — not string matching▼
① Concept

Agentic Loop Control SD 1.1

The core loop pattern: call the model, inspect stop_reason, route accordingly. Loop continuation is a programmatic decision, never a language-parsing decision.

② Key Fact

stop_reason: "tool_use" → extract the tool call, execute it, append tool_result to messages, call the model again. stop_reason: "end_turn" → break the loop. These are the only two values that control loop flow.

③ Common Trap

Checking response text for words like "DONE", "Task complete", "Finished" to decide when to stop. String matching on model output is non-deterministic — the model rephrases freely and will break your regex.

④ Real-World Scenario

A customer support agent handles flight rebooking. Mid-session the user shifts from "cancel my flight" to "reschedule instead." The loop terminates when it detects "Confirmed" in the model's reply — but the rescheduling tool call was never executed, leaving the booking in a broken state.

⑤ Correct Execution

Check stop_reason programmatically:
if resp.stop_reason == "tool_use":
  result = call_tool(resp)
  messages.append(tool_result_msg)
elif resp.stop_reason == "end_turn": break
Never inspect resp.content[0].text for control flow.

⑥ Anti-Pattern

if "done" in resp.content[0].text.lower(): break — fatally brittle. Model output is non-deterministic; a single rephrasing like "Task accomplished" bypasses this check and loops forever, or "I'm done thinking" exits prematurely.

D1Tool Result Message RoleRole must be "user" — not "tool" or "assistant"▼
① Concept

Tool Result Role SD 1.1

After executing a tool, the result must be appended as a user-role message with a tool_result content block. The turn alternation rule (user → assistant) applies here too.

② Key Fact

The only valid message roles are "user" and "assistant". Tool results use role "user" with content type "tool_result" and must include the matching tool_use_id.

③ Common Trap

Using role: "tool" or role: "assistant" for the tool result message. The API returns a 400 error immediately — no retry will help until the role is corrected to "user".

④ Real-World Scenario

A CI code-review pipeline intermittently returns 400 errors after bash tool calls. The team spends two days blaming rate limits and network instability before discovering every tool result was appended with role: "tool".

⑤ Correct Execution

messages.append({"role":"user","content":[{"type":"tool_result","tool_use_id":tool.id,"content":result}]})
This is the only valid structure. The model never sees the tool result if the role is wrong — it errors before reaching the model.

⑥ Anti-Pattern

{"role":"tool","content":result} — invalid role. Also wrong: {"role":"assistant","content":...} which would put two consecutive assistant turns in history, violating turn alternation. Both cause immediate 400 API errors.

D1Hub-and-Spoke OrchestrationCoordinator orchestrates only — subagents get minimum context▼
① Concept

Hub-and-Spoke Multi-Agent SD 1.2

The coordinator is a pure orchestrator — it breaks work into tasks, delegates to specialist subagents, and synthesizes results. It never directly executes file writes, API calls, or tool operations itself.

② Key Fact

Subagents receive minimum necessary context for their specific task — never the full coordinator conversation history. Each subagent's allowedTools is restricted to what that specific task requires.

③ Common Trap

Passing the coordinator's full conversation history to every subagent. This causes token explosion, cross-task context contamination, and hallucinations where one subagent's findings bleed into another's analysis.

④ Real-World Scenario

A research synthesis system coordinator forwards its 200K-token conversation history to 8 parallel research subagents. Context limits are hit after 3 subagents complete; early results contaminate later agents' independent analysis, producing circular citations.

⑤ Correct Execution

Coordinator creates targeted task payloads per subagent: {"task":"analyze_Q3_revenue","sources":["doc_A","doc_B"],"allowedTools":["Read","search_db"]}. Each subagent receives only its specific question and relevant sources. Coordinator synthesizes using only final subagent output objects.

⑥ Anti-Pattern

Forwarding full_coordinator_history to subagents. Also: coordinator directly calling write_file() or commit_code() instead of delegating. Coordinators that execute are no longer coordinators — they become single-agent bottlenecks with all the risks of both patterns.

② Key Fact

Task calls in one coordinator message = concurrent execution. Task calls across separate coordinator turns = sequential execution. The distinction is entirely in how many Task calls appear in a single model response.

③ Common Trap

Emitting one Task call per coordinator response turn, expecting the runtime to batch them. Each separate turn creates a synchronization barrier — the coordinator waits for each subagent before spawning the next, eliminating all parallelism.

A CI/CD validation pipeline spawns 5 test-runner subagents sequentially — one per coordinator turn. The pipeline takes 25 minutes. After refactoring to emit all 5 Task calls in a single coordinator response, it runs in 5 minutes. Architecture was right; turn structure was wrong.

for svc in services: claude.messages.create(tools=[task]...) — each loop iteration waits for completion before spawning the next. Even if intent is parallel, sequential loop calls create sequential execution. The fix is emitting all Task calls in one message, not a loop.

① Concept

Hooks in settings.json fire as bash scripts before (PreToolUse) or after (PostToolUse) tool execution. A non-zero exit from a PreToolUse hook blocks the tool call entirely — the model never executes it.

② Key Fact

Exit 0 = allow tool. Exit non-zero = block tool, return error to model. This is infrastructure-level enforcement — it cannot be bypassed by model instructions, context pressure, or CLAUDE.md rules.

③ Common Trap

Adding safety policies to CLAUDE.md: "never delete files without confirmation" or "always ask before pushing to main." These are advisory — the model deprioritizes them under long context, high-autonomy prompts, or conflicting instructions.

④ Real-World Scenario

A production DevOps agent runs rm -rf /data/logs during automated cleanup. The system prompt says "always confirm before deleting." During a long autonomous session, the model skips the confirmation. The policy was advisory; the enforcement was absent.

settings.json PreToolUse hook script:

  echo "Blocked: destructive rm"; exit 1
fi
Tool blocked at infrastructure level regardless of model state.

⑥ Anti-Pattern

CLAUDE.md or system prompt "safety" instructions for destructive operations. Natural language policies are not enforcement mechanisms. Any instruction that relies on the model choosing to comply is advisory, not mandatory. Hooks are the only mandatory mechanism.

① Concept

PostToolUse Hook (Result Normalization) SD 1.5

PostToolUse hooks intercept tool results after execution and before the model receives them. Use for: timestamp conversion, status code translation, output truncation, field filtering.

② Key Fact

Normalization is infrastructure work, not model work. Converting Unix timestamps, HTTP status codes, or API error codes in a PostToolUse hook costs zero model tokens and produces deterministic output. Asking the model to "interpret" raw output costs tokens and introduces variance.

③ Common Trap

System prompt instruction: "When you see a large integer above 1,700,000,000, treat it as a Unix timestamp and convert it." The model occasionally misidentifies port numbers (17000x) as timestamps, producing wrong date outputs.

④ Real-World Scenario

An operations monitoring agent receives raw Unix timestamps and HTTP status codes in tool results. The system prompt instructs the model to interpret them. After a large context session, the model starts misidentifying 17001 (a port number) as a near-2024 date, producing nonsensical log timestamps.

⑤ Correct Execution

PostToolUse hook script transforms output before the model sees it:
epoch_to_iso() { date -d @$1 +%Y-%m-%dT%H:%M:%SZ }
Result reaches model as "timestamp":"2024-11-15T14:32:00Z" — no interpretation needed, no token cost, no variance.

⑥ Anti-Pattern

Any system prompt that asks the model to "interpret", "translate", or "convert" raw tool output values. Format normalization is deterministic infrastructure work. Delegating it to the model adds token cost, introduces variance, and creates a class of bugs that only appear after long context sessions.

Two distinct session patterns: --resume continues an existing named session with full history. fork_session creates a new independent branch starting from a shared analysis baseline.

② Key Fact

MCP Error Structure SD 2.2

MCP tool error responses require two programmatic signals: isError: true so the model knows the call failed, and isRetryable to tell it whether retrying makes sense.

② Key Fact

isRetryable: false for business rule errors (RIDE_FULL, INVALID_INPUT — retrying won't help). isRetryable: true for transient errors (network drop, rate limit — retry is appropriate). The model uses these flags to decide its next action.

③ Common Trap

Returning {"message":"RIDE_FULL"} with no isError flag. The model treats this as a successful tool response and attempts to "confirm the booking" — acting on the error string as if it were valid booking data.

⑥ Anti-Pattern

Swallowing errors into success-shaped responses. Any error payload without isError: true is indistinguishable from success to the model. Also: setting isRetryable: true on a RIDE_FULL error causes the model to retry the same booking request, wasting API calls and confusing the user.

② Key Fact

tools=[t1,t2,...,t18] — passing all available tools to one agent context. Also: splitting tools by count rather than by semantic domain (e.g., "first 5 tools go to Agent A, next 5 to Agent B"). Split by capability cohesion, not by arbitrary count.

⑥ Anti-Pattern

tool_choice="auto" in any deterministic pipeline. Also: using "any" when you need a specific schema — "any" lets the model pick among all available tools, which may not be the extraction tool. Use forced-name mode for schema-critical pipelines.

Blind retry: messages.append({"role":"user","content":"invalid, try again"}). "Be conservative," "only flag clear issues," "use your judgment." Cache breakpoint after dynamic content (user messages, tool results). Cache breakpoint in the middle of static content (splits cache unnecessarily). Models reliably process information at the beginning and end of long context windows. Information positioned in the middle of large aggregated inputs is systematically deprioritized — it may be omitted from synthesis, summaries, and conclusions.

② Key Fact

When aggregating multiple subagent outputs or documents into a single synthesis context, position the most critical finding first, supporting detail after. Do not rely on the model to surface the most important content from middle positions through relevance scoring.

③ Common Trap

Appending subagent outputs in discovery order (alphabetical, chronological, arbitrary) and expecting the model to surface the most critical finding regardless of its position in the aggregated context. Middle-position critical findings are routinely omitted from executive summaries.

④ Real-World Scenario

A legal research synthesis agent aggregates 8 source documents in alphabetical order. The critical regulatory risk finding is in document #4 — middle position. The executive memo omits it. A partner cannot sign off, the memo is rejected, and the team discovers the finding was present but positioned where the model deprioritizes it.

⑤ Correct Execution

Coordinator explicitly reorders aggregated input by criticality before synthesis: highest-risk findings first, supporting evidence after. Or uses a named critical finding block: <critical_finding>Regulatory exposure identified in Doc 4...</critical_finding> followed by supporting documents. Position is not cosmetic — it is architectural.

⑥ Anti-Pattern

Appending subagent outputs in arbitrary order (return order, alphabetical, creation time) and trusting the synthesis model to surface the most important content. Implicit relevance ranking does not override the position effect. Critical findings must be explicitly positioned at the start of any large aggregated context.

D5Escalation TriggersStructural criteria only — frustrated tone is NOT a reliable escalation signal▼
① Concept

Structural Escalation Logic SD 5.2

Escalation triggers must be structural: explicit human request, policy gap (agent has no procedure for this case), or inability to make progress after N defined attempts. Sentiment-based triggers are probabilistic and produce false positives at high volume.

② Key Fact

Sentiment analysis classifies tone, not need. An angry expert asking a solvable question does not need escalation. A polite novice with a policy gap does. The only reliable escalation signals are: explicit request, structural inability to resolve, or defined retry exhaustion.

③ Common Trap

Using negative sentiment score as an escalation trigger: "if sentiment < -0.4, escalate." This floods human queues with tickets from users who were frustrated but would have been resolved on the next response. High false-positive escalation destroys human agent efficiency.

④ Real-World Scenario

A support agent escalates 40% of tickets because users say "ridiculous" or "unacceptable." Post-analysis: 50% of escalated tickets were resolved on the very next agent message. Human agents are overwhelmed with unnecessary tickets. Team adds sentiment filtering thinking it's a feature; it's creating a workload crisis.

⑤ Correct Execution

Escalation decision tree — all structural, zero sentiment:
1. User explicitly requests human? → escalate.
2. No agent procedure covers this case (policy gap)? → escalate.
3. Same issue unresolved after ≥3 attempts? → escalate.
No sentiment scoring. No tone analysis. Binary structural criteria only.

⑥ Anti-Pattern

if sentiment_score < threshold: escalate() — sentiment-based escalation. Also: escalating on first failure without a retry attempt (over-escalation). Also: never escalating regardless of inability to progress (under-escalation). Structural criteria produce consistent, measurable escalation rates. Sentiment scoring produces noise.

D5Confidence & Source AttributionEvery claim needs a source. Synthesis must preserve claim-source mappings through compression.▼
① Concept

Claim-Source Mapping SD 5.5

Subagents must output source attribution alongside every finding. Synthesis agents must preserve those mappings through compression. Confidence levels must be criteria-defined (based on observable evidence), not vibes-based (based on model self-assessment).

② Key Fact

"Various documents" is not source attribution. Each claim requires a specific document, section, or data point reference. Confidence levels require explicit criteria: "high = direct quote, no ambiguity. medium = strongly implied. low = inferred, requires verification." Vague confidence is unusable downstream.

③ Common Trap

Synthesis agents that compress findings without preserving source mappings. The final report presents claims as synthesized facts with no traceable source — useless for legal, compliance, or audit contexts where every assertion must be verifiable.

④ Real-World Scenario

A legal research synthesis produces a liability estimate memo. The source attribution reads "based on several reviewed documents." A partner cannot sign off without knowing which documents support the estimate. The memo is rejected and must be redone from scratch — with proper per-claim source attribution built into the subagent output schema.

⑤ Correct Execution

Subagent output schema includes mandatory attribution fields:
{"claim":"liability exposure in Q3","source":"Contract_v3.pdf §14.2","confidence":"high","confidence_reason":"Direct clause, unambiguous language"}
Synthesis agent output schema: same fields preserved. Never compress to "various sources."

⑥ Anti-Pattern

{"finding":"medium liability exposure","source":"various documents"} — vague attribution is not attribution. Also: synthesizing multiple claims into one attributed to a single source when they came from different documents. Each claim requires its own source. Synthesis may aggregate; it may not fabricate provenance.

D5Tool Output TrimmingKeep only relevant fields — 40-field API responses waste thousands of tokens per call▼
① Concept

Context Economy SD 5.3

Every tool response appended verbatim to conversation history occupies permanent context. A 40-field API response providing 2–3 relevant fields wastes ~2,300 tokens per call. After 10 calls: 23,000 tokens of irrelevant data crowding out recent context.

② Key Fact

Context is a finite, non-renewable resource within a session. Every irrelevant token is a token taken from useful information. Tool output trimming — extracting only relevant fields before appending — is the most impactful single optimization for long agentic sessions.

③ Common Trap

Appending raw API responses verbatim to conversation history: "it's easier to let the model pick out what it needs." The model does not filter what it stores. Each verbatim response occupies context permanently until compaction. Context fills faster than expected and degrades sooner.

④ Real-World Scenario

A carpool booking agent calls get_ride_details() 8 times per session. Each raw response is ~2,400 tokens (40 fields). After 8 calls, 19,200 tokens of irrelevant ride metadata fill the context window. The agent begins losing track of user preferences stated in early turns. Compaction hits early; recent decisions are dropped.

⑤ Correct Execution

PostToolUse hook extracts relevant fields before model sees the response:
relevant = {"ride_id":r["id"],"seats":r["available_seats"],"departs":r["departure_time"],"driver":r["driver_name"]}
Model receives 80 tokens, not 2,400. Session lasts 25× longer before context pressure affects behavior.

⑥ Anti-Pattern

Appending any verbose API response verbatim to conversation history. Also: "trimming" by asking the model to summarize its tool results — this uses the model for work that should be done deterministically in a PostToolUse hook. Trimming is infrastructure work, not model work. It should happen before the model sees the output, not after.

🔑 Core Concepts Tested

  • Detecting intent shifts mid-conversation without losing prior context
  • Routing to specialist sub-handlers based on current flow state
  • Escalation = clean state reset, not a crash
  • Stale button guard: expired sessions must surface friendly errors, not NPEs
  • Tool results must always be appended before continuing the loop

🔵 Our Project Is the Blueprint

  • BotFlow enum = 50+ conversation states (exact support routing analogue)
  • StateManager (Caffeine cache, 30-min TTL) = per-session memory
  • CallbackHandler Map = intent router (one action → one handler)

  • stateManager.reset() = graceful escalation to main menu (clean slate)
📁 Project File: carpool-bot/handler/SessionRecoveryHandler.java

Flow-sensitive actions (post-ride steps, rating, edit-time) → show "Session Expired" message and call stateManager.reset().
Non-flow-sensitive actions (MY_PROFILE, PENDING_HUBS) → recover with fresh UserState.initial() and proceed normally.

This is precisely the escalation/recovery pattern a support agent needs. Distinguish: recoverable errors (fresh session) vs. context-dependent errors (must restart the flow).
JAVA — Escalation Pattern (SessionRecoveryHandler analogue)
// carpool-bot/handler/SessionRecoveryHandler.java
// The same pattern used in a support agent context:

public boolean isFlowSensitive(String action) {
    // These actions require valid state fields (e.g., departureTime, rideId)
    // If missing, the "conversation" cannot continue — must escalate
    return POST_RIDE_ACTIONS.contains(action)
        || RATING_ACTIONS.contains(action)
        || EDIT_TIME_ACTIONS.contains(action);
}

// In the dispatcher:
UserState state = stateManager.get(chatId);
if (state == null || state.getFlow() == BotFlow.IDLE) {
    if (isFlowSensitive(action)) {
        // Escalation: can't recover — tell user to restart
        bot.sendMessage(chatId, "⚠️ Session expired. Please start over from the main menu.");
        stateManager.reset(chatId);   // ← clean slate
        return;
    }
    // Soft recovery: non-sensitive action works with fresh state
    state = UserState.initial(carpoolUserId);
}
// Continue routing with valid state...

⚖️ Core Architectural Trade-Off — Session Freshness vs. State Continuity

Freshness: Always resetting state on any ambiguity is safest — no NPEs, no stale data. But users lose their progress and must restart entire flows (bad UX).

Continuity: Persisting state longer increases risk of stale button exploits and context drift. A user tapping an old button with outdated ride data could corrupt a booking.

Our resolution: Classify actions as flow-sensitive vs. non-flow-sensitive. Reset only when required. This is the correct answer on the exam — never a blanket strategy.

When Claude Code tries to Write or Edit any file, settings.json fires flyway-gate.sh first. If the target is an existing Flyway migration, the hook exits 1 and blocks the write — even if the model has already decided to make the change. This is programmatic enforcement, not prompt guidance.
BASH — flyway-gate.sh (PreToolUse Hook for Code Generation Safety)
#!/usr/bin/env bash
# .claude/hooks/flyway-gate.sh
# Fires on every Write/Edit tool call.
# Blocks editing existing Flyway migrations — must create new ones.

FILE="${CLAUDE_TOOL_INPUT_FILE_PATH:-}"

if [[ "$FILE" =~ db/migration/V[0-9]+__.+\.sql$ ]]; then
  # Is this an existing file? (not a new one being created)
  if [[ -f "$FILE" ]]; then
    echo "ERROR: Editing existing Flyway migration '$FILE' is forbidden."
    echo "Create a new migration with the next version number instead."
    exit 1   # ← blocks the Write/Edit tool call
  fi
fi

exit 0  # ← allows all other writes

⚖️ Core Architectural Trade-Off — Automation Speed vs. Review Gates

Speed: Removing all hooks and running Claude Code in auto-approve mode generates code faster. Useful for solo prototyping on throwaway branches.

Safety: Every hook adds latency (shell process startup ~50ms). For 10 file edits, that's ~500ms overhead. On a large generation task, hooks run dozens of times.

Our resolution: Hooks guard only irreversible or high-risk operations (migrations, module boundaries, destructive bash). Low-risk edits (Java logic, tests) pass without hooks. This minimises overhead while maximising safety at the boundaries that actually matter.

// carpool-service/scheduler/PendingBookingScheduler.java
// Production ops monitoring pattern — maps directly to incident response

@Scheduled(fixedDelay = 30 * 60 * 1000, initialDelay = 5 * 60 * 1000)
public void checkPendingBookings() {
    // Step 1: Poll — query for "incidents" (pending bookings past SLA)
    List stalePending = bookingRepository
        .findPendingOlderThan(Instant.now().minus(15, MINUTES));

    for (Booking booking : stalePending) {
        int reminderCount = booking.getReminderCount();

        // Step 2: Evaluate threshold — how many reminders sent?
        if (reminderCount >= 3) {
            // Step 3: Escalate — auto-timeout after max reminders
            eventPublisher.publishEvent(new BookingTimedOutEvent(booking));
        } else {
            // Step 4: Escalate progressively — send reminder DM to driver
            eventPublisher.publishEvent(
                new BookingReminderEvent(booking, reminderCount + 1));
        }
        // Step 5: Record outcome — idempotency guard prevents double-escalation
        booking.setReminderCount(reminderCount + 1);
        bookingRepository.save(booking);
    }
}
// fixedDelay (not fixedRate) ensures previous run completes before next starts
// initialDelay prevents startup overlap with ride-expiry scheduler

Low frequency (e.g., every 30 min): Minimal DB load. But SLA violations are only detected up to 30 minutes late — unacceptable for time-sensitive operations.

Our resolution: Different schedulers use different cadences based on urgency: RideDepartureReminderScheduler runs every 5 min (time-critical), PendingBookingScheduler every 30 min (moderate urgency), StaleAnnouncementRefreshScheduler every 4 hours (low urgency). import anthropic

client = anthropic.Anthropic()

def chat_with_history(history: list, user_message: str,
                      max_tokens_budget: int = 150_000) -> tuple[str, list]:
    # Append new user message (never mutate — create new list)
    new_history = history + [{"role": "user", "content": user_message}]

    # Sliding window: if history is too long, keep system context + last N turns
    # analogous to StateManager's 30-min TTL evicting old sessions
    estimated_tokens = estimate_tokens(new_history)
    if estimated_tokens > max_tokens_budget:
        # Keep first 2 turns (context-setting) + last 10 turns (recent context)
        new_history = new_history[:2] + new_history[-10:]

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=4096,
        system=PERSISTENT_SYSTEM_PROMPT,  # ← never changes, cache this
        messages=new_history
    )

    assistant_reply = response.content[0].text
    # Append assistant response — always append, never modify
    final_history = new_history + [{"role": "assistant",
                                     "content": assistant_reply}]
    return assistant_reply, final_history

def run_unit_tests(module: str, test_class: str = None) -> dict:
    cmd = f"mvn test -pl {module} -Dgroups='!integration'"
    if test_class:
        cmd += f" -Dtest={test_class}"

    result = subprocess.run(cmd, capture_output=True, text=True, timeout=120)  # timeout!

    # Return structured output — not raw stdout (model can't reliably grep Maven output)
    return {
        "exit_code": result.returncode,
        "passed": result.returncode == 0,
        "failed_tests": extract_failed_tests(result.stdout),  # structured list
        "duration_seconds": extract_duration(result.stdout),
        "isError": result.returncode != 0,
        "errorCategory": "TEST_FAILURE" if result.returncode != 0 else None
    }
# Model reads passed:true/false — not "BUILD SUCCESS" text

⚖️ Core Architectural Trade-Off — Execution Isolation vs. Test Realism

Full isolation (H2 in-memory): Tests run anywhere, no Docker required, fast startup (~2s vs ~15s for MySQL). But SELECT FOR UPDATE is silently ignored — concurrency bugs pass undetected. False safety.

Real environment (MySQL): Tests match production exactly. Concurrency bugs are caught. Requires Docker, port 3308, setup time. Cannot run in all CI environments without infrastructure.

Our resolution: Two-tier test strategy. Unit tests (-Dgroups="!integration") run against H2 — fast, no deps, suitable for local and standard CI. Concurrency/integration tests (@Tag("integration")) run only in environments with real MySQL — Docker-based CI only. Never test pessimistic locking against H2: it will lie to you.
