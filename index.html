🔄 1.1 The Agentic Loop Lifecycle

An agent is not a single API call — it is a loop that continues until the model signals completion. Understanding stop_reason is the most tested concept in this domain.

⏹️ stop_reason Values

  • tool_use — model wants to call a tool; loop MUST continue by appending results
  • end_turn — model finished; loop should terminate
  • max_tokens — context limit hit; handle gracefully
  • stop_sequence — custom stop token matched; usually terminal

📜 Conversation History Rules

  • Tool results MUST be appended before the next API call
  • Role alternation: user → assistant → user → assistant
  • Tool result role = user, not tool
  • Never skip a tool result — the model loses context
  • Each tool result maps to its tool_use_id
🗺️ Canonical Loop Pattern
PYTHON — Canonical Agentic Loop (CCA-F Reference Pattern)
messages = [{"role": "user", "content": user_input}]

while True:
    response = client.messages.create(
        model="claude-opus-4-7",
        max_tokens=4096,
        tools=tools,
        messages=messages
    )

    # Always append the assistant's full response
    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        # Model is done — extract final text and exit
        final = next(b.text for b in response.content if b.type == "text")
        break

    if response.stop_reason == "tool_use":
        # Execute every tool call the model requested
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,      # ← must match the request id
                    "content": result
                })

        # Append results as a USER message before the next call
        messages.append({"role": "user", "content": tool_results})
        # Loop continues — model now sees the results
    else:
        break  # max_tokens / stop_sequence — handle accordingly
🚨

Anti-Pattern #1 — Skipping Tool Results

Calling the API again without appending the tool result is the most common agentic bug. The model re-enters without knowing what the tool returned, leading to hallucinated results or infinite loops. The exam will test this — always append results before the next call.

🔵 Project Blueprint — How car-e-pool-api Implements an Agentic Pattern

The Telegram bot implements a stateful, event-driven agentic loop across CallbackHandler, MessageHandler, StateManager, and the sub-handlers. The conversation state (UserState) is the analogue of conversation history.

Telegram Update
→
CallbackHandler / MessageHandler
→
Route by BotFlow enum
→
Sub-Handler (tool execution)
→
StateManager.save()
→
Bot sends response (end_turn analogue)

🔄 Loop Continue — tool_use analogue

In the bot, a "tool call" is any handler that mutates UserState and expects another user interaction to continue the flow:

  • handleDateSelected() → sets flow=DEPARTURE_TIME, sends time picker
  • handleRideTimeSelected() → sets flow=ORIGIN, sends hub list
  • Each step waits for the next update (next "tool result")

🛑 Loop Terminate — end_turn analogue

The loop terminates when a terminal step is reached:

  • handleConfirmPostRide() → publishes ride, calls stateManager.reset()
  • handleCancelPostRide() → discards draft, calls stateManager.reset()
  • BotFlowHelper.showMainMenu() → always calls stateManager.reset()

🏛️

Architect Wisdom — Tool Choice Eliminates Ambiguity

When you need structured output, use tool_choice: {type: "tool", name: "..."} to force the model into a specific tool call. This is more reliable than asking the model to "respond in JSON" in a system prompt. The model cannot call a different tool, cannot return plain text — the structure is enforced at the protocol level, not via prompt persuasion.

🕸️ 1.2 Orchestration Topologies

📍 Single Agent

One model, one loop, all tools available. Best for focused tasks with clear termination. Used in: AiService.parseRideRequest() — single Ollama call, immediate result.

🕸️ Hub-and-Spoke (Exam Favourite)

Coordinator agent delegates to specialist subagents via tool calls. Coordinator never executes directly — it orchestrates. Car-e-pool-api parallel: Claude Code is the coordinator; .claude/agents/*.md define the 9 specialist spokes.

🔗 Sequential Pipeline

Agent A's output becomes Agent B's input. No shared state. Used in: NotificationService event chain — BookingService commits → ApplicationEventPublisher fires → NotificationService sends DM.

🪝 1.3 PreToolUse / PostToolUse Lifecycle Hooks

Hooks fire before or after tool execution and can block, modify, or log. They enforce policies programmatically — stronger than system-prompt instructions because they execute outside model context.

🔒 Our settings.json Hook Config

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command",
                    "command": "bash .claude/hooks/guard-bash.sh" }]
      },
      {
        "matcher": "Write",
        "hooks": [
          { "type":"command","command":"bash .claude/hooks/flyway-gate.sh" },
          { "type":"command","command":"bash .claude/hooks/module-boundary-check.sh" }
        ]
      },
      {
        "matcher": "Edit",
        "hooks": [
          { "type":"command","command":"bash .claude/hooks/flyway-gate.sh" },
          { "type":"command","command":"bash .claude/hooks/module-boundary-check.sh" }
        ]
      }
    ],
    "Stop": [
      { "hooks": [{ "type":"command",
                    "command": "bash .claude/hooks/vault-writeback.sh" }] }
    ]
  }
}

🛡️ What Each Hook Enforces

  • guard-bash.sh — blocks rm -rf, DROP TABLE, --force-push
  • flyway-gate.sh — enforces V#__description.sql naming; blocks editing any existing migration file
  • module-boundary-check.sh — blocks illegal cross-module Java imports (e.g., carpool-bot importing carpool-web)
  • vault-writeback.sh — on session stop: auto-creates dispatch log in memory/dispatch-logs/
💡

Exam Key

Hooks exit non-zero to block the tool call. Exit zero to allow. The model cannot override a blocking hook via prompting — this is the core advantage over system-prompt policies.

❌ Weak — Prompt-Only Policy
# In CLAUDE.md or system prompt:
"IMPORTANT: Never edit existing Flyway
migration files. Always create new ones
with the next version number."

// Problem: Model can "forget", be confused
// by context, or be talked out of it.
// Zero enforcement at execution time.
✅ Strong — Hook-Enforced Policy
# In settings.json PreToolUse for Write/Edit:
bash .claude/hooks/flyway-gate.sh

# flyway-gate.sh checks the target file path:
if [[ "$FILE" =~ V[0-9]+__.+\.sql$ ]]; then
  if [[ "$FILE" == *"db/migration"* ]]; then
    # Existing migration → block with exit 1
    echo "ERROR: Editing existing migration forbidden"
    exit 1
  fi
fi
# New file or non-migration → allow with exit 0
🔒 1.4 Context Isolation Between Coordinator and Subagents
📌

The Principle

A coordinator agent should pass only the minimum necessary context to each subagent. The coordinator synthesizes results itself — it does not dump its full conversation history into every subagent call. This keeps subagent prompts focused, reduces token cost, and prevents context poisoning.

✅ Correct — Targeted Handoff

# Coordinator sends to db-engineer agent:
"Add a NOT NULL column `group_message_posted_at
TIMESTAMP` to the rides table. The existing
migration is V44. Write V45."

# Agent receives ONLY:
# - the specific task
# - the relevant constraint
# No conversation history, no other modules' code.

❌ Wrong — Context Dumping

# Coordinator sends to db-engineer agent:
[Full 50-message conversation history]
[All 6 module CLAUDE.md files]
[All 44 existing migration files]
"...and also add the column."

# Problem: Agent wastes tokens re-reading irrelevant
# context, may be distracted by unrelated patterns,
# and response quality degrades.

🏛️

Architect Wisdom — Prompt vs Hook for Safety Policies

For any policy that protects data integrity (never drop a table, never edit a migration, never cross module boundaries), use a hook, not a prompt instruction. Prompts are advisory. Hooks are enforced. The exam distinguishes between "programmatic enforcement" (hooks, tool schema constraints, tool_choice) and "weak prompt guidance" (system prompt instructions asking the model to behave a certain way).

🏗️ 2.1 Model Context Protocol Architecture

🖥️ MCP Host

The application that embeds Claude (Claude Code, your IDE, your app). Manages the MCP client lifecycle. In our project: Claude Code CLI is the host when you run it in car-e-pool-api/.

🔌 MCP Client

Lives inside the host. Maintains a 1:1 connection with one MCP server. Handles transport negotiation. Managed by the host automatically — you don't write client code directly.

⚙️ MCP Server

Exposes Tools, Resources, and Prompts to the model. Can be a local process (stdio) or remote HTTP server. Example: @modelcontextprotocol/server-github gives Claude GitHub API access.

🚨

Exam Trap — Never Hardcode Credentials

Always use ${ENV_VAR_NAME} syntax in MCP config files. The actual value is resolved from the environment at runtime. Hardcoding tokens in .mcp.json is a security failure — the file is committed to the repo and the token is exposed. The exam will test whether you know credentials belong in environment variables, not config files.

📝 2.3 Writing High-Fidelity Tool Descriptions

Tool descriptions are the primary mechanism for routing disambiguation. A vague description causes the model to pick the wrong tool or to not use a tool at all.

❌ Vague Tool Description
{
  "name": "search_rides",
  "description": "Search for rides",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" }
    }
  }
}
// Problems:
// - "Search for rides" could mean anything
// - Model doesn't know when to prefer this
//   over a general DB query tool
// - No examples, no error conditions stated
// - Free-form "query" string is unstructured
✅ High-Fidelity Tool Description
{
  "name": "search_rides_by_direction",
  "description": "Search active carpool rides for a specific
direction and time window. Use this (not search_rides_by_hub)
when the user specifies a commute direction (home-to-work or
work-to-home) rather than specific hub names. Returns paginated
RideResponse list sorted by departure time. Returns empty list
(not an error) when no rides match.",
  "input_schema": {
    "type": "object",
    "properties": {
      "direction": {
        "type": "string",
        "enum": ["HOME_TO_WORK", "WORK_TO_HOME"],
        "description": "Commute direction"
      },
      "from_datetime": { "type": "string", "format": "date-time" },
      "to_datetime":   { "type": "string", "format": "date-time" },
      "min_seats":     { "type": "integer", "minimum": 1 }
    },
    "required": ["direction", "from_datetime", "to_datetime"]
  }
}

🔴 2.5 Structured Error Recovery Matrix

When a tool fails, returning a plain error string forces the model to parse natural language to decide what to do next. Returning structured error metadata enables deterministic retry logic.

PYTHON — Rich Error Response Pattern
# ❌ Anti-pattern: plain string error
return "Error: booking failed"

# ✅ Correct: structured error with metadata
return {
    "isError": True,
    "errorCode": "RIDE_FULL",
    "errorCategory": "BUSINESS_RULE",  # BUSINESS_RULE | NETWORK | AUTH | VALIDATION
    "isRetryable": False,              # model knows not to retry
    "userMessage": "This ride is now full. Please search for another.",
    "metadata": {
        "rideId": 42,
        "availableSeats": 0,
        "suggestion": "search_rides_by_direction"  # guide the model's next step
    }
}

# isRetryable: True examples:
# - NETWORK timeout → retry with backoff
# - RATE_LIMIT → wait then retry
# - OPTIMISTIC_LOCK → re-fetch and retry

# isRetryable: False examples:
# - RIDE_FULL → do not retry, search instead
# - SELF_BOOKING → do not retry, inform user
# - DUPLICATE_BOOKING → do not retry
Error from Our DomainerrorCategoryisRetryableModel Action

DuplicateBookingExceptionBUSINESS_RULEfalseShow existing booking instead
InvalidRideStateExceptionBUSINESS_RULEfalseInform user of required state

🏛️

Architect Wisdom — Tools Are Your API Contract

Every tool description is a promise to the model about when to use that tool and what to expect back. Vague descriptions cause routing failures. Missing error metadata causes blind retries. Think of tool schemas as a typed API — the richer the types and descriptions, the more reliably the model routes. In production, tool descriptions matter as much as system prompts.

# carpool-service Module Guide

## Purpose
Business logic, DTOs, MapStruct mapper, event system, schedulers, and AI service.
Depends on: carpool-repository. Depended on by: carpool-bot, carpool-admin.

## Key Patterns
- Events: publish via ApplicationEventPublisher, listen with @Async + @TransactionalEventListener(AFTER_COMMIT) + @Transactional(REQUIRES_NEW)
- DTOs: all in dto/response/ as Java records; EntityMapper generates via MapStruct
- Plate masking: enforced in EntityMapper — first 3 chars + "***"

## When Adding New Business Logic
1. Run /flyway-migration if DB schema changes
2. Run /new-event if async notification needed
3. Run /spring-boot-review before committing

## Common Gotchas
- REQUIRES_NEW is mandatory on all event listeners — without it, IllegalTransactionStateException
- VehicleResponse always has masked plate — never expose Vehicle.plateNumber in a DTO directly

SKILL.md Format — /new-event skill example
# Skill: /new-event
# Trigger: "adding a domain event", "async notification", "fire event"

## Checklist

### Step 1 — Define the event record in RideEvents.java
```java
// Add inside RideEvents final class:
public record MyNewEvent(Ride ride, String reason) {}
```

### Step 2 — Publish in the service (inside @Transactional method)
```java
eventPublisher.publishEvent(new RideEvents.MyNewEvent(ride, reason));
```

### Step 3 — Listen with the exact 3-annotation stack (no substitutions)
```java
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void onMyNewEvent(RideEvents.MyNewEvent event) {
    // Safe to call Telegram API here — runs after commit, in new transaction
}
```

## Why These Annotations Matter
- @Async: notification doesn't block the booking transaction
- AFTER_COMMIT: Telegram only fires after DB write succeeds
- REQUIRES_NEW: independent transaction for notification status tracking

🗂️ Plan Mode vs Direct Execution

  • Plan Mode: model outlines steps, asks for approval before any file edits
  • Direct: model executes immediately (reads, edits, runs commands)
  • Use Plan Mode for: multi-module changes, Flyway migrations, security config changes
  • Use Direct for: single-file bug fixes, documentation, test additions
  • Our CLAUDE.md enforces: "present planned file changes and wait for approval before editing"

The Alternating Turn Rule

Few-shot examples must alternate user → assistant → user → assistant. You cannot have two consecutive user messages or two consecutive assistant messages. Each example is one full exchange. The final message is always user (the actual query).

🏗️ 4.3 System Context Design — AiService Audit

The current AiService.parseRideRequest() in the project uses a Spring AI ChatClient with an inline system prompt. Here's how to structure it optimally:

JAVA — Optimized AiService System Prompt Structure
// carpool-service/ai/AiService.java
@Service
public class AiService {

    // System prompt components — ordered for cache efficiency:
    // 1. Static role + context (most cacheable)
    // 2. Semi-static rules (cacheable within session)
    // 3. Dynamic per-request data (never cached)

    private static final String SYSTEM_STATIC = """
        You are a ride-detail extractor for a Philippine carpooling app.
        The app serves commuters in Metro Manila.
        Users write in Filipino, Taglish, or English.

        Key domain facts:
        - "Home to work" direction = morning commute, before noon
        - "Work to home" direction = evening commute, after noon
        - Common locations: Sucat, Paranaque, BGC, Makati, Taguig, QC
        - Filipino time words: "bukas"=tomorrow, "ngayon"=today, "mamaya"=later today
        - "Magpost"/"mag post" indicates intent to post a ride (driver)
        """;

    private static final String EXTRACTION_RULES = """
        Extraction rules:
        1. If direction is ambiguous, infer from time (morning=HOME_TO_WORK, evening=WORK_TO_HOME)
        2. If a field cannot be determined, return null — do not guess
        3. Times are 24h format. "7am"=07:00, "6pm"=18:00
        4. Seats: look for numbers near "seat", "tao", "pasahero"
        5. Contribution: look for peso amounts near "each", "tig", "per person"
        """;

    public ParsedRideRequest parseRideRequest(String userMessage) {
        // System prompt = static + rules (both cache-eligible)
        // User message = dynamic (never cached, always appended)
        return chatClient
            .prompt()
            .system(SYSTEM_STATIC + "\n" + EXTRACTION_RULES)
            .user(userMessage)
            .call()
            .entity(ParsedRideRequest.class);
    }
}

Architect Wisdom — Schema Over Instructions

The single most important prompt engineering insight: every behavioral constraint you can move from a natural language instruction into a schema constraint, do it. "Please output valid JSON" is weak. tool_choice: {type: "tool"} is absolute. "Maximum 4 seats" in prose is advisory. "maximum": 4 in a JSON schema is enforced by the API. Move constraints down the stack — from prose to schema to type system — at every opportunity.

Exam Key — Graceful Degradation

The parsed.isEmpty() check is critical. AI parsing is best-effort — network failures, bad JSON, model errors are all possible. The bot never hard-depends on AI availability. This is the correct production pattern: AI augments the flow, it doesn't gate it.

💰 5.1 Strategic Prompt Caching

Prompt caching stores processed prompt segments on Anthropic's servers for 5 minutes (Haiku) or longer (Opus/Sonnet). Cached tokens cost ~10% of normal input token price. The key skill is knowing where to place cache breakpoints.

📍 Cache Breakpoint Rules

  • Breakpoints are placed at the end of a static section
  • Everything before a breakpoint is eligible for caching
  • Dynamic content (user input, timestamps) goes AFTER the last breakpoint
  • TTL: 5 minutes — re-use within 5 min = cache hit
  • Max 4 cache breakpoints per request

💸 Cost Model

  • Cache write: 1.25× normal input cost (paid once)
  • Cache hit: ~0.10× normal input cost (paid each reuse)
  • Break-even: ~2 requests to recoup write cost
  • Best for: system prompts, long code files, tool definitions that don't change per request
PYTHON — Correct Cache Breakpoint Placement for car-e-pool-api Agent
messages = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=8192,
    system=[
        # Breakpoint 1: Static role + project overview (~500 tokens)
        # This never changes — cache it aggressively
        {
            "type": "text",
            "text": STATIC_ROLE_AND_PROJECT_OVERVIEW,
            "cache_control": {"type": "ephemeral"}  # ← breakpoint 1
        },
        # Breakpoint 2: CLAUDE.md content (~2000 tokens)
        # Changes rarely — cache with 5-min TTL
        {
            "type": "text",
            "text": read_claude_md_content(),
            "cache_control": {"type": "ephemeral"}  # ← breakpoint 2
        },
        # Breakpoint 3: Tool definitions (~800 tokens)
        # Same tools per session — cache them
        {
            "type": "text",
            "text": format_tool_definitions(all_tools),
            "cache_control": {"type": "ephemeral"}  # ← breakpoint 3
        },
        # NO breakpoint here: session-specific context added fresh each call
        {
            "type": "text",
            "text": f"Current branch: {git_branch}\nModified files: {modified_files}"
            # ← dynamic, never cached
        }
    ],
    messages=conversation_history  # conversation itself is never cached
)

description: Why BookingService uses SELECT FOR UPDATE instead of optimistic locking

BookingService.createBooking() acquires a pessimistic write lock via
rideRepository.findByIdWithLock(rideId) — a SELECT FOR UPDATE query.

**Why:** Integration tests proved that optimistic locking (version column)
resulted in a "last write wins" race condition under concurrent bookings.
H2 in-memory DB ignores SELECT FOR UPDATE — concurrency tests must use
real MySQL at localhost:3308.

**How to apply:** Never replace findByIdWithLock() with findById() in
BookingService. If adding a new booking-like feature (e.g., waitlist),
use the same lock acquisition pattern. See [[adr-003-event-listeners]]
for the complementary notification safety pattern.

Architect Wisdom — Cache What's Static, Stream What's Dynamic

The mental model for prompt caching: anything that would be the same across 10 API calls should be cached. System prompts, tool definitions, CLAUDE.md content, large reference documents — these are cache candidates. User messages, timestamps, current file diffs, search results — these are never cached. The cache_control breakpoint goes at the boundary between static and dynamic content. Moving it one block earlier or later can double your cache hit rate.
